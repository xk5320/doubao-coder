# 13 · 反馈与同步状态：对拍（differential parity）

> 目标：扩展侧边栏里显示的「执行反馈」和「同步状态」，与豆包桌面端对话区**逐块、逐字一致**；
> 并且这件事要能自动验证，不靠肉眼截图。

---

## 1. 豆包一条助手回复的真实结构（实测）

对话区里每条消息是 `[data-testid=union_message]`。助手回复的 `message_content` 不是一整段 Markdown，
而是一串按 `data-plugin-identifier` 标记的块：

| block_type | 含义 | 关键节点 |
|---|---|---|
| `10091` | 同步状态（计时分隔线） | `[data-testid=preamble-elapsed-timer]` → `已处理 5 分 52 秒` / `共用时 4 分 55 秒` |
| `10040` | 一步执行反馈（thinking 步骤） | 单行标题，右侧 `expand-result-btn` 可展开 |
| `10000` | 正文 | `[data-testid=message_text_content]`（`data-streaming=true` 表示仍在流式） |
| `10080` | 快捷回复 | 空的占位块，跳过 |

两个容易踩的点：

1. **运行中 vs 结束后布局不同**。
   运行中步骤和正文直接挂在 `message_content` 下；结束后它们被折进 `10091` 的 `bodySlot`。
   两种情况 `querySelectorAll('[data-plugin-identifier]')` 的前序顺序都等于视觉顺序。
2. **折叠时内容不在 DOM 里**。
   `preamble-elapsed` 折叠（`data-message-content-collapsed=true`）时，`innerText` 只有计时那一行。
   所以定时同步会先调用 `expandStepsJs()` 点开它，再读块。

## 2. 统一模型：`ReplyBlock`（`src/bridge/blocks.ts`）

```ts
type ReplyBlock =
  | { kind: 'text'; text: string }        // 正文 Markdown
  | { kind: 'status'; text: string }      // 计时：已处理 / 共用时
  | { kind: 'step'; text: string;         // 反馈步骤标题
      detail?: string;                    // 展开后的输出
      state: 'done' | 'running' | 'error' }
  | { kind: 'code'; text: string; output?: string }; // 旧通道兼容
```

配套纯函数（Node 侧可直接单测）：

- `parseElapsedSeconds('已处理 5 分 52 秒')` → `352`；支持 秒 / 分秒 / 时分秒，读不到返回 `-1`；
- `formatElapsed(352)` → `5 分 52 秒`（与豆包同样的空格与量词）；
- `isFinishedElapsed('共用时 4 分 55 秒')` → `true`；
- `blocksToMarkdown(blocks)` → 只拼正文，用于保存 / PTC 解析。

---

## 3. 提取规则（`readLastReplyJs`）

页面上下文里执行，返回 `{ count, text, streaming, images, progress, progressSeconds, done, executing, busy, blocks }`：

1. 取最后一条 `receive_message`（`index` 参数可回看历史消息，默认 -1）；
2. 计时从 `preamble-elapsed-timer` 原样取（不再由正则重写）；
3. 遍历 `message_content` 下的 `[data-plugin-identifier]`：
   - `10091` → `status`（只记一次，避免重复）；
   - `10040` → `step`；标题取 `innerText` 压成一行；`正在…` = running；
     短标题且含「超时/失败/出错/错误」= error；**命令行标题不据此判失败**；
   - `10000` → `text`，用 `window.__dcMd()` 还原围栏/表格/行内 code；
4. `text` = 所有正文块用空行拼接；`done` = 计时以「共用时」开头。

图片、生成中、确认弹窗等仍走原有独立字段，不进 `blocks`。

## 4. 同步状态的对齐点

| 位置 | 豆包 | 改前 | 改后 |
|---|---|---|---|
| 运行中 | `已处理 5 分 52 秒` | `已处理 0 秒` 起跳、只在 <60s 正确 | 原样透传，秒数由豆包上报值 + 本地增量 |
| 结束 | `共用时 4 分 55 秒` | `已处理 4 分 55 秒` | `共用时 …`，并收掉动效 |
| 是否还在跑 | 停止按钮 / 计时 / `正在执行代码` | `progressSeconds > 0` → 完成的任务也永远为真 | `done` 优先，再看 busy / streaming / executing |

面板里计时以 `turnReportedSeconds + 本地增量` 计算，每 500ms 重绘一次；
`syncStatus` 消息（扩展 → Webview）携带 `{ text, seconds, done }`，文本直接来自页面。

## 5. 对拍工具

```powershell

node tools/parity.mjs              # 对拍最后一条助手回复一次
node tools/parity.mjs --watch 30   # 连续 30 秒，每秒一次（任务执行中观察块在长）
```

- **生产侧**：直接执行扩展编译产物 `out/bridge/md-extractor.js` 的 `readLastReplyJs`；
- 比较项：计时文案、秒数、done、executing、块数、每块类型、步骤标题、步骤状态、正文（去 Markdown 符号后逐字）。

退出码：有差异 = 1。可直接进 CI。

## 7. 边界与维护

- **步骤详情**：折叠的 step 在 DOM 里没有输出内容，`detail` 只有用户点开后才读得到；
  对拍只比较标题与状态，不把 detail 作为必填项。
- **图片 / 生成类卡片**：不在 `blocks` 里，仍由 `images` / `generating` 字段单独处理。
- **用户消息**：不参与对拍（右侧气泡是另一种渲染）。
- **豆包改版**：若 `block_type` 编号变化，先跑 `node tools/parity.mjs --all`，
  失败信息会直接指出是计时、块数还是某一块的类型/文案，按提示改 `readLastReplyJs` 与参考侧即可。

## 8. 多标签页与「新建对话」（0.32.1）

豆包客户端是多标签页的，同一时刻的 `/json/list` 里可能同时有：

- `doubao://doubao-chat/chat/<id>` —— 客户端内对话页（要驱动的就是它）
- `doubao://doubao-chat/chat` —— **刚点「新对话」后的空会话页**（没有 id，也没有结尾斜杠）
- `https://www.doubao.com/chat/<id>` —— 网页版标签页（隐藏，DOM 相似但不能当后端）
- `doubao://doubao-background/`、官网、iframe……

旧逻辑 `find(url.includes('doubao-chat'))` 有两个坑：

1. 新建对话后的 `/chat` 路由不匹配 `/chat/` 前缀，会误判为“没有对话页”，退到隐藏的网页版标签页 →
   表现就是**扩展说已发送、豆包界面没切过去**，而客户端里还留着的一排标签页看起来“没动”。
2. 多个对话标签页时取第一个，可能取到后台页。

现在统一走 `pickChatPage()`（`src/bridge/cdp.ts`）：

```
chatPageCandidates(): 只保留 doubao://doubao-chat/...；没有才退网页版 / 豆包页
pickChatPage():       多候选时逐个连上去读 document.visibilityState，优先 visible
发送前:                Page.bringToFront，把目标页切到前台
```

`createDesktopConversation` 点「新对话」后若客户端把新会话开在新标签页，会重新扫描前台页并校验
`union_message === 0`，不再把“切到了新标签页”误判为失败。

## 9. 计时器必须从真实起点开始（0.32.1）

复现：新建任务后扩展先上报 `busy`（连接 / 切换会话中），此时还没有任何一轮回复；
旧代码在 `tickTurnDivider` / `finishAssistant` 里用 `Date.now() - turnStartedAt`，而 `turnStartedAt = 0`，
于是把 **epoch 秒数**当成了处理时长 → 「已处理 498624 小时 20 分 16 秒」。

现在的规则（`elapsedSecondsNow()`）：

- 有豆包上报的秒数：`上报值 + 本地增量`；
- 没有上报但有回合起点：`now - 起点`；
- 两者都没有：**0**；
- 负数 / 非有限 / 超过 7 天：一律按 0（超过 7 天基本可确定是把时间戳当秒用了）。

另外：`applyState` 收到 `busy` 且没有回合时，用当前时间建起点；`clear`（新建对话/任务）会同时清掉
分隔线、计时器和起点，避免上一轮的残留。

## 10. 分块容器必须按「轮」隔离（0.32.2）

同步器每秒下发的是**整条回复**的分块快照，界面必须整体替换。

旧实现用 `messagesEl.querySelector('.ast-blocks:last-child')` 找容器：
计时分隔线在忙时会被移到对话最底部（0.31.1 的改动），`.ast-blocks` 就不再是 last-child，
查找必然失败 → 每次同步都 `appendChild` 一份新容器 → 界面上整段内容重复。

现在：

- `nativeBlocksWrap` 记录**本轮**容器；同一轮内重复 `blocks` 只整体替换；
- 发送新一轮（`send` / 收到 `user` 回显）时置空，新建容器，**上一轮回答保留**；
- `clear` 时一并清空引用。

回归用例：同一轮连发两次 `blocks` 断言只有一份容器；再发一轮断言上一轮内容仍在。

## 11. 「已处理」的位置（0.32.3）

豆包把计时放在**该条回答的顶部**（用户消息之后、正文之前），运行中是 `已处理 4 分 32 秒`，
结束后原地变 `共用时 4 分 32 秒`。

扩展此前把同一条分隔线移到对话最底部（0.31.1 为了"别看起来停在中途"），与豆包不一致。现在的规则：

- 发送时在用户消息之后创建本轮分隔线，正文/步骤分块追加在它下面；
- 同一轮内原地更新计时，不再移动；
- **每条回答各一条**：新一轮新建，上一轮的「共用时」留在原位；
- 结束后 `turnFinished = true`，陈旧的 `busy` 不会把「共用时」重新切回「已处理」。

## 12. 执行反馈图标（0.32.4）

豆包每类动作的步骤行图标不同：`</>` 终端、书本（读取文件）、放大镜（查找内容）、铅笔（写入/修改），
运行中的步骤用转圈/沙漏，失败用警告。

扩展的映射规则（`inferStepIcon` / 前端 `stepIconKind`）：

1. **先按标题语义**：`已执行代码`→code、`已读取`→read、`已查找文件内容`→search、`已写入/修改`→edit、
   浏览器→browser、技能/插件→skill；
2. **再看页面真实图标**：`shellexec`/`shellview`→code、`fileview`→read（用于「Unity 项目信息」这类无前缀步骤）；
3. 都识别不出 → `›`。

渲染：`.ast-step-icon.icon-<kind>`，SVG 用 currentColor 描边（不引用豆包 CDN 资源），
运行中换成 `.step-spin` 转圈，失败为 `!`。

## 13. 步骤行为什么会「消失」（0.32.5 兜底）

三条路径都会造成「只有正文、没有步骤行」，现在各有一道保险：

1. **数据侧**：豆包把步骤折进 `preamble-elapsed` 的折叠体时，折叠状态下 DOM 里没有步骤节点。
   `SyncPoller` 现在每次 tick 前都调用一次 `expandStepsJs()`（内部 2s 节流），
   不再只在连接时展开一次。
2. **渲染侧**：任何一块渲染抛错都不能影响后面的块。`renderAst` 的每个块单独 `try/catch`，
   失败时把该块渲染成纯文本（`.ast-step-fallback`），步骤标题至少还在。
3. **定位侧**：`turnContentAnchor()` 只返回 `nativeBlocksWrap`（本轮容器），
   不再拿「最后一个 .ast-blocks」当锚点——那可能是上一轮的回答，会把新计时线插到上面。

排查：日志文件 `<扩展日志目录>/doubao.log`，每次分块同步会写
`同步分块 steps=<步骤数> kinds=<块类型列表>`。若 `steps=0`，问题在数据/抓取；
若 `steps>0` 但界面没有，问题在渲染，可按上面第 2 条继续查。

## 14. 系统提示词里的「当前模型」（0.32.6）

桌面端通道下，真正生效的模型是**豆包界面里选中的那个**（工具栏显示 `DeepSeek V4.1 Flash · 高`），
不是 Ark 的 `config.model`。此前 `buildSystemPrompt` 用的是 `config.model`（默认 `doubao-seed-1.6-flash`），
用户看到的注入提示词和界面选择不一致。

现在：

1. `runDesktop` 先 `ensureDesktopWorkMode()`（对齐模式与模型），再 `buildSystemPrompt(config, effective)`；
2. `pickEffectiveModel`（`src/chat/model-label.ts`）统一决定：
   - 本地电脑：面板记住的 `taskModel` > 配置的 `desktop.model` > Ark `model`；
   - 对话模式：桌面端「快速/专家」；
3. `ensureDesktopModelChoice` 不再因为「配置里没写模型」提前返回，总会读一次桌面端当前模型；
4. 行内改写同样把桌面端当前模型传进提示词。

## 15. 「90 秒没有回复」误报（0.32.7）

现象：步骤/计时一直在动，面板却弹「90 秒内没有看到豆包的回复」，点「继续」又正常。

原因：`askDesktop` 的判定只看 `snap.text`（正文）。长任务里模型可能连续几十秒只跑命令、
正文为空，90 秒硬阈值一到就抛错。

现在改由 `isStalled()`（`src/bridge/activity.ts`）判定，只有以下同时成立才报：

- `sawReply === false`；
- 没有停止按钮、也没有「正在执行代码」；
- 距上次任何活动（正文/分块/计时/执行态）超过 90 秒。

计时或步骤在变 = 仍在干活，继续等（总时长仍受 `doubao.desktop.timeoutMs` 约束）。

## 16. 一个 10040 块里装着整段执行过程（0.32.8）

实测：一个回合的几十条步骤（每行 21px）都在**同一个 `block_type:10040`** 里，
每行是 `[data-thinking-box="step-message"]`，可见标题在 `div.truncate`。

旧实现把整个块当一条步骤（`norm(node.innerText)`），结果：

- 只显示一行，标题是几十行拼接；
- 前缀重复：`正在执行代码 正在执行代码 $f=…`（块里既有 sr-only 标签又有可见标题）。

现在：

1. 对每个 `10040`，枚举可见的 `step-message` 行（宽高 > 0，折叠隐藏的跳过）；
2. 标题取 `div.truncate` 的 textContent（没有才退回行 innerText）；
3. 状态（`正在` → running、短标题含失败词 → error）、图标（行内 `shellexec/fileview`）、详情都按行取；
4. 连续相同的 `state|title` 去重。

对拍工具参考实现也改成逐行（按行 `getBoundingClientRect` 排序），真机 40 块 / 38 步 0 差异。

## 17. 执行中标题的渐隐与颜色过渡（0.32.9）

豆包的超长步骤标题不是省略号，而是**右侧渐隐**（容器上的 mask），执行中的行更明显。

扩展里的实现（`media/chat.css`）：

- `.ast-step.is-running .ast-step-title`：渐隐起点 82%，给「正在…」留出可读宽度；
- `transition: color .25s ease`：状态切换时颜色平滑过渡；
- `.ast-step.is-open .ast-step-title`：取消 mask、允许换行（展开详情时看全文）。

图标仍是 14×14、描边 1.35 的 SVG；运行中图标是转圈，失败是 `!`。

## 18. 执行过程为什么没展开（0.32.10）

实测：运行中 `preamble-elapsed` 的展开按钮是 `disabled`，`data-message-content-collapsed="true"`，
步骤节点不在 DOM 里；回合结束后按钮才可用，点一下才会把整段执行过程渲染出来。

旧链路：同步器每 tick 展开（点击无效）→ 回合结束 → 6 次无变化 → 空闲停止 → **永远不会再展开**。

现在三条路径都补了：

1. `askDesktop` 收尾前 `expandStepsJs()` + 重读分块，有变化立刻 `onBlocks`；
2. `SyncPoller` 空闲要停之前最后展开一次，成功则继续同步；
3. `watchDesktop` 每轮读之前展开。

另外：`chat.css/chat.js` 的 webview URI 带版本号，面板标题显示 `v0.32.10`，便于确认当前加载的构建。

## 19. 「90 秒没动静」先重试（0.32.11）

用户要求：重试几次「继续说」都没反应，才提示。实现：

- `stallDecision({...isStalled, retries, maxRetries=2})`：`ok` / `retry` / `give-up`；
- `askDesktop` 首次判定卡住 → `retry`：重试计数 +1、`lastChange` 重置（再等 90 秒）；
- 重试 2 次后仍卡住 → `give-up`，提示「重试 2 次后仍没有看到…」；
- 任何正文/步骤/计时活动都会把重试计数清零；
- 单轮 `timeoutMs` 到点时，若仍在执行/最近 60 秒有活动：不停止豆包、不报超时，转为持续同步。

## 20. 自动「继续说」（0.32.12）

回合结束（`assistant_done`）会渲染建议 chip；其中「继续说 / 继续」会在按钮上倒计时（默认 5 秒），到点自动发送，
让豆包继续执行，面板继续同步状态。

- 配置：`doubao.autoContinue`（默认开）、`doubao.autoContinueSeconds`（默认 5，0 关闭）；
- 取消：手动发送、停止、输入框按键、收到新输出（`assistant_delta`）、清空/切换会话、`state.busy` 变真；
- 测试钩子：`window.__DC_AUTO_CONTINUE_MS`（harness 只推进 ≤40ms 定时器时用 0）。

## 21. 历史列表的加载/失败状态（0.32.13）

打开「历史对话」时，面板先进入 loading：`historyLoading = true`，列表区渲染
`.history-loading`（旋转 spinner + 「正在加载豆包对话列表…」），同时面板消息里先发
`{ type:'historyMenu', loading:true }`，读完再发完整列表。

- 首次加载：本地为空且豆包有列表 → 自动切到「豆包对话」；

## 22. 计时只从「发送」开始（0.32.14）

现象：只粘贴了附件（还没发送），面板就出现「已处理 0 秒 •••」，而且时间不走。

原因：粘贴/同步技能会调用 `showPending('正在添加附件')`，它顺手创建了分隔线；
但这一轮并没有开始，`turnFinished` 还是上一轮结束的状态，`tickTurnDivider` 直接返回 → 静态 0 秒。

修复：`showPending()` 只处理等待提示，**不再创建分隔线**；
计时从 `startAssistant()`（真正发送后）或豆包上报的 `syncStatus` 开始；
已结束回合的「共用时」不会被附件操作改回「已处理」。

## 54. 本地图片转 data URL（0.32.46）

`openDesktopChat(index, titleHint)`：

## 62. 纯文本里的管道表（0.32.54）

`blocks` 通道只会把文本交给 `markdown()`（行内渲染），不会解析表格。

`takePipeTable(text)`：

- 扫描以 `|` 开头的行，下一行必须是 `| --- |` 分隔行；
- `splitPipeRow` 拆单元格；表格前/后的文本分别用 `markdown()` 渲染；
- 表格用 `buildAstTable`，与 `table` 块共用。

---

## 63. 流式表格渲染（0.32.55）

`assistant_delta` 走 `markdown(streamingBuffer)` 行内渲染，表格仍是原文。

新增 `renderMarkdownWithTables(text)`：循环 `takePipeTable`，
表格前文字用 `markdown()`、表格用 `buildAstTable()`、继续处理 after；
`renderStreaming` 与 `finishAssistant` 都使用它。

## 64. 压成一行的表格还原（0.32.56）

某些通道会把表格换行折叠成空格，行表格检测失败。兜底：

- 取第一个 `|` 之后的内容按 `|` 拆单元格；
- 找第一段连续 `---` 单元格，数量 N 即列数；
- 头部 = 前 N 个；剩余按 N 个一组还原行；第一个 `|` 前文字作为 before。

## 66. 空单元格分行（0.32.58）

压成一行的表格里，行与行之间常出现空单元格 `| |`；兜底逻辑先按空单元格切段作为行，再补齐列数；
没有空单元格时退回按列数分组。
