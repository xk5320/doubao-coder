# 桌面端登录态直连（免 API Key，和桌面版同一套登录）

> 目标：**不申请 ARK_API_KEY**，直接用你已经在豆包桌面端登录的账号，在 VS Code 侧边栏里对话。
> 本文记录这条路为什么成立、怎么实现、验证到了什么程度、以及边界在哪。

---

## 1. 先回答"为什么不能像 CodeBuddy 那样直接连远端 web"

这是关键区别，值得说清楚：

| | CodeBuddy | 豆包 |
|---|---|---|
| 扩展对接的"远端 web" | 腾讯云面向 **IDE 产品**的官方后端（有登录协议、有对外契约） | `www.doubao.com` 的**网页端私有接口**（只服务官方 Web/桌面客户端） |
| 登录方式 | 官方 OAuth / 账号登录，拿到 token 调**给第三方用的 API** | 网页会话 Cookie + 请求签名（`msToken` / `a_bogus` 之类）+ `metasecml.dll` / `bdticket.dll` 设备指纹 |
| 第三方直连可行性 | 设计如此 | 需要技术调研签名算法，且随客户端/风控更新失效；违反用户协议 |

也就是说：**"对接远端 web"本身不是难点，难点是"远端 web 只认它自己的客户端"**。
自己造一个客户端去调它，等于长期对抗风控。

那我们换个思路：**不造客户端，直接把你已经登录的那个客户端当后端用。**

---

## 2. 这条路为什么成立（实测证据）

豆包桌面端就是 Chromium 147（见 `02-架构与实现.md`），因此它天生支持 Chrome DevTools Protocol：

```
$ Doubao.exe --remote-debugging-port=9222
$ curl 127.0.0.1:9222/json/version
{
  "Browser": "Chrome/147.0.7727.149",
  "Protocol-Version": "1.3",
  "webSocketDebuggerUrl": "ws://127.0.0.1:9222/devtools/browser/ad3d60b0-…"
}
```

页面目标（实测）：

| type | url | 说明 |
|---|---|---|
| page | `doubao://doubao-chat/chat/38454362503650306` | **对话页**（自定义 scheme，内部渲染 `www.doubao.com` 的应用） |
| page | `doubao://doubao-background` | 后台页 |
| iframe | `https://www.doubao.com/drive-iframe/drive/home/` | 云盘等子应用 |

关键点：**登录态、签名、风控全在这个页面里由官方 JS 完成**。
我们只做三件事：把文字写进输入框 → 点发送 → 把回复读回来。

## 3. DOM 契约（实测，全部来自真实页面）

豆包前端自带 `data-testid` 测试钩子，比 class 名（`container-qX9Csx` 这种带哈希的）稳定得多：

| 用途 | 选择器 | 备注 |
|---|---|---|
| 输入区容器 | `[data-testid="chat_input_input"]` | 内部是 TipTap/ProseMirror |
| 编辑器 | `[data-testid="chat_input_input"] [contenteditable="true"]` | `div.tiptap.ProseMirror` |
| 发送按钮 | `[data-testid="chat_input_send_button"]` | 有内容时才出现 |
| 新建对话 | `[data-testid="create_conversation_button"]` | |
| 消息列表 | `[data-testid="message-list"]` | **虚拟滚动**（只渲染视口内消息） |
| 每条消息 | `[data-testid="union_message"]` | |
| 用户消息 | `[data-testid="send_message"]` | |
| 助手消息 | `[data-testid="receive_message"]` | |
| 正文 | `[data-testid="message_text_content"]` | **带 `data-streaming="true/false"`** ← 天然的"生成中"信号 |
| 模型/模式 | `[data-testid="chat_input_action_model"]` / `chat_input_action_mode` | |

两个坑，已踩过并修复：

1. **不能靠"消息条数"判断新回复**。列表是虚拟滚动的，发送后重排会让条数**变少**，
   于是 `count > baseline` 永远不成立（第一版就是这么失败的）。
   正确做法：用"最后一条助手消息的文本"做基线 + `data-streaming` 判断结束。
2. **`message_text_content.innerText` 会把代码块拍平**（围栏和语言标记都丢）。
   做法：在页面里注入 `window.__dcMd(node)`，把 `pre/code/h1-6/li/table/内联 code` 还原成 Markdown。

## 4. 实现（扩展里的落点）

```
src/bridge/
├─ ws.ts            自研极简 WebSocket 客户端（RFC6455 文本帧/分片/ping-pong，无第三方依赖）
├─ cdp.ts           CDP 最小客户端：/json/version、/json/list、Runtime.evaluate、Input.*、Page.*
├─ desktop.ts       probeDesktop() / askDesktop()：探测、写入、发送、流式读回、停止
└─ md-extractor.ts  注入页面的 __dcMd()（DOM → Markdown）+ readLastReplyJs()
```

调用链：

```
侧边栏输入 ──▶ panel.handleUser()
                 ├─ authMode==='ark'    → AgentLoop（原 Ark 通道，需要 Key）
                 └─ authMode==='desktop' → runDesktop()
                        ├─ buildSystemPrompt() + buildUserContent()   （工作区上下文照旧注入）
                        └─ askDesktop()
                              ├─ listTargets → 找 doubao-chat 页面
                              ├─ 等编辑器就绪 → focus + 全选删除 → Input.insertText
                              ├─ 点 [data-testid=chat_input_send_button]（失败则回车兜底）
                              └─ 每 200ms 读最后一条 receive_message
                                    ├─ text 变化 → onDelta(增量) → webview 流式渲染
                                    └─ data-streaming=false 或 2.5s 静止 → 结束
```

配置项：

| 配置 | 默认 | 说明 |
|---|---|---|
| `doubao.authMode` | `desktop` | `desktop` = 免 Key；`ark` = 走官方 API |
| `doubao.desktop.port` | `9222` | 调试端口 |
| `doubao.desktop.exePath` | 自动推导 | `%LOCALAPPDATA%\Doubao\Application\app\Doubao.exe` |
| `doubao.desktop.newChat` | `false` | 每次提问前是否新开对话（PTC 多轮建议设 `true`） |
| `doubao.desktop.timeoutMs` | `180000` | 等回复上限 |
| `doubao.ptc.enabled` | `true` | 是否启用 PTC 文本工具调用 |
| `doubao.ptc.maxRounds` | `4` | PTC 最大工具轮数（每轮会多一条会话消息） |

命令：

- **`豆包: 以调试端口启动桌面端`** —— 用 `--remote-debugging-port=9222` 拉起豆包，并轮询到就绪；
- **`豆包: 连接豆包桌面端（免 Key）`** —— 探测并报告（浏览器版本/页面标题/是否已登录/是否有输入框）。

## 6. 边界与代价（必须知道）

1. **必须让豆包以调试端口启动**。豆包是单实例应用：已经开着的话，再执行带参数的启动会被"转发给已有实例"吞掉。
   → 正确姿势：**完全退出豆包** → 命令面板执行「豆包: 以调试端口启动桌面端」。
   一旦这样启动，本机任何进程都能通过 9222 连上这个浏览器上下文（只监听 127.0.0.1，但仍是本地信任边界），
   **不要长期开着**；用完退出即可。
2. **会操作你正在用的窗口**。发送前会 `Page.bringToFront`（避免后台节流），所以会抢一次焦点；
   回复会写进你当前的会话（或 `doubao.desktop.newChat=true` 时新开一个）。
3. **依赖页面结构**。`data-testid` 是官方测试钩子，比 class 稳，但**不是公开契约**；
   豆包大版本更新后可能需要重新核对（用 `tools/cdp_inspect*.py` 可一键重新取证）。
4. **工具调用走 PTC**。桌面端通道拿到的是纯文本，官方不会返回 `tool_calls`，所以默认启用
   **PTC（Programmatic Tool Calling）**：模型在回复里写 ` ```tool ` 代码块，扩展解析执行后再把
   `<tool_result>` 发回同一会话。这样免 Key 也能读写工作区（详见 `04-PTC模式.md`）。
   想要最稳的结构化调用，仍建议 Ark 模式。
5. **行内补全不可用**。官方客户端不对外提供 FIM 接口，`authMode=desktop` 时补全会自动跳过
   （想用补全就配 Ark Key，两者可以并存：对话走桌面端、补全走 Ark）。
6. **合规**。这不是"绕过鉴权登录"，也不是"伪造签名"：用的是你自己的账号、官方客户端、官方页面，
   没有任何凭据被导出或复用。但**自动化操作客户端**仍可能与你所在环境的豆包用户协议存在张力，
   建议只用于个人开发环境，不要打包分发"共用账号"的版本。

## 7. 和 Ark 路线怎么选

| | 桌面端登录态（本文） | Ark API Key |
|---|---|---|
| 需要 Key | ❌ | ✅ |
| 计费 | 走你账号的现有额度 | 按 token 计费 |
| 稳定性 | 中（页面结构变更需适配） | 高（官方契约） |
| 工具调用（读写工作区） | ❌（走 MCP 反向） | ✅（内置 7 个工具） |
| 行内补全 | ❌ | ✅ |
| 需要开着豆包 | ✅ | ❌ |
| 适合 | 个人、不想申请 Key、想复用已有订阅 | 团队/产品化/需要稳定与自动化 |

两者在扩展里**并存**，一个下拉框（`doubao.authMode`）就能切；也可以对话用桌面端、补全用 Ark。
