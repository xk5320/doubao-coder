# 09 · 界面一比一方案（可执行的三种重做路线）

> 目标：扩展里的工作界面与交互，和豆包客户端**看起来、用起来完全一样**。
> 结论先说：**只有"截屏投送 + 输入转发"能做到真正的一比一**，另外两条路要么做不到，要么越界。

---

## 0. 为什么现在的界面不可能"一模一样"

现在的实现是**用我们自己写的 HTML/CSS 去模仿**豆包的排版（消息气泡、`</> 已执行代码`、任务块、共用时分隔线…）。
模仿得再像，也是两套渲染器：

| 差异来源 | 例子 |
|---|---|
| 排版规则不同 | 行高、字号、代码块圆角、列表缩进 |
| 富内容不同 | 表格、引用卡片、图片排版、附件、可折叠区 |
| 交互不同 | 悬停操作条、右键菜单、快捷键、拖拽、滚动吸附 |
| 状态机不同 | 生成中/待确认/排队/中断的真实状态与动画 |

只要渲染器不同，就永远会有"这里差一点"。要 1:1，必须**让同一个渲染器出图**。

## 1. 三条路线对比（实测数据在 §2）

### 路线 A：截屏投送 + 输入转发（推荐）

把豆包窗口的画面用 CDP 的 `Page.startScreencast` 推成 JPEG 帧，塞进 VS Code Webview 的 `<img>`；
把用户在面板里的鼠标/键盘事件按坐标映射回豆包窗口（`Input.dispatchMouseEvent` / `Input.dispatchKeyEvent` / `Input.insertText`）。

```
┌───────────── 豆包客户端（Chromium 147）─────────────┐
│  React 前端（官方代码，官方渲染）                    │
│    Page.startScreencast ──► JPEG 帧（CDP 事件）      │
│    Input.*  ◄── 坐标/按键（CDP 命令）                │
└──────────────────────────────────────────────────────┘
        ▲ websocket                          │
        │                                    ▼
┌───────┴──────── 扩展（Node） ────────┐   ┌── Webview ──┐
│ 帧转发（base64 → postMessage）        │──►│ <img> 画布  │
│ 输入转发（坐标换算）                  │◄──│ mousemove   │
└──────────────────────────────────────┘   └─────────────┘
```

- **一致性**：像素级 100%（就是同一个 UI）
- **交互**：鼠标/键盘/滚轮/中文输入 全部可转发；拖拽、悬停、右键需要额外事件映射
- **代价**：不是原生控件（文字不可选、无法被屏幕阅读器读取、主题不跟随 VS Code）
- **可补**：叠一层"文本层"——用现有 DOM 读取器把纯文本按位置铺一层透明文字（PDF 阅读器就是这么干的）

### 路线 B：复用官方前端代码（rex86 架构移植）

把豆包 web 前端的 前端资源整理、在扩展里跑起来。

- **做不到**：它依赖自家接口 + 鉴权 + 风控（`bdticket` / `metasecml` 等），
  要跑起来就得**重放私有 API、伪造签名**——这是越界行为，也不是"移植"而是"盗链"。
- 结论：**放弃**。

### 路线 C：DOM 快照影子渲染

把页面的 DOM 子树 + computed style 序列化，注入 webview 渲染。

- 静态能看，**动态交互全失效**（React 事件、受控输入框、虚拟列表滚动）。
- 只适合"生成报告/截图存档"，不适合工作界面。

## 2. 路线 A 的可行性实测（本机，1365×910 视口）

### 2.1 单帧截图（`Page.captureScreenshot`）

| 质量 | 平均耗时 | 平均体积 | 最大体积 |
|---|---|---|---|
| JPEG 60 | **131 ms** | 68.7 KB | 68.8 KB |
| JPEG 75 | 124 ms | 86.4 KB | 86.4 KB |
| JPEG 90 | 132 ms | 129.9 KB | 130.0 KB |

轮询式 7~8 fps，带宽 ~0.5 MB/s。

### 2.2 推流（`Page.startScreencast`，推荐）

```
maxWidth=1000 / maxHeight=700 / quality=70 / everyNthFrame=1
→ 4 秒 189 帧（≈47 fps），平均 66.7 KB/帧
```

把 `everyNthFrame` 调到 4~6 即可稳定 8~12 fps、带宽 ~0.15 MB/s，CPU 占用可接受。
**结论：完全可行，且比轮询省。**

## 3. 推荐架构（路线 A + 文本层）

### 3.1 新增一个视图：`豆包镜像`

- 侧边栏图标切换或在面板内加「镜像」按钮 → 新 Webview View `doubao.mirror`
- 画面区：`<img id="cast">`，每帧 `img.src = 'data:image/jpeg;base64,' + frame`
- 交互区：透明覆盖层接收事件 → `postMessage({type:'mirrorInput', ...})` → 扩展转发

### 3.2 消息协议（扩展 ↔ Webview）

| 方向 | 消息 | 说明 |
|---|---|---|
| → 面板 | `{type:'cast', data, w, h, ts}` | 一帧画面（base64，不含前缀） |
| → 面板 | `{type:'castStop', reason}` | 停流（窗口关闭/断线） |
| ← 扩展 | `{type:'mirrorInput', kind:'move'|'down'|'up'|'wheel'|'key'|'text', x, y, ...}` | 归一化坐标 0..1 |
| ← 扩展 | `{type:'mirrorResize', scale}` | 面板缩放级别变化 |
| ← 扩展 | `{type:'mirrorText'}` | 请求"文本层"（可选） |

### 3.3 输入转发要点

1. **坐标映射**：面板坐标 → 视口坐标，必须按 `clientWidth/clientHeight` 归一化后再乘豆包视口尺寸（`Page.getLayoutMetrics`）
2. **滚轮**：`Input.dispatchMouseEvent{type:'mouseWheel', deltaX, deltaY}`
3. **键盘**：只转发"非输入法"按键；文本输入用 `Input.insertText`（避免中文 IME 与 key 事件冲突）
4. **粘贴**：走现有 `navigator.clipboard` 读取 + `insertText`
5. **拖拽**：`mousePressed → mouseMoved×N → mouseReleased`，中间补 `buttons` 位

### 3.4 性能预算

| 项 | 预算 |
|---|---|
| 帧率 | 8~12 fps（静止时降到 1 fps） |
| 单帧 | ≤ 80 KB（`maxWidth=1000, quality=70`） |
| 带宽 | ≤ 1 MB/s（本地环回） |
| 输入延迟 | < 30 ms（本地 CDP 往返 ~5 ms） |

静止检测：比较连续两帧 base64 的哈希，相同则跳过推送（豆包 screencast 本身也只在变化时推）。

## 4. 与现有代码的衔接

| 已有能力 | 复用方式 |
|---|---|
| `bridge/cdp.ts`（`CdpSession`，含事件队列） | 直接用：`Page.startScreencast` 走事件流 |
| `bridge/ws-stream.ts` | 可复用其"事件 → 面板"管道结构 |
| `bridge/desktop.ts`（`probeDesktop`、`askDesktop`） | 保留：文本式通道仍适合"只要答案"的场景 |
| `bridge/desktop-history.ts` | 保留：历史列表/切换对话 |
| 现有 chat 面板 | 保留为「文本模式」；镜像模式是并列的第二种视图 |

**两种模式并存**：
- **文本模式**（现有）：可选中、可复制、走 VS Code 主题 —— 适合"读答案"
- **镜像模式**（新增）：像素级一致 —— 适合"操作豆包、看它怎么干活"

## 6. 风险与边界

| 风险 | 说明 | 处理 |
|---|---|---|
| 最小化窗口 | Chromium 不给隐藏窗口出帧/派发输入 | 镜像模式启动时 `Page.bringToFront` + 提示"请勿最小化" |
| 隐私 | 镜像会把豆包窗口里**其他会话**也显示出来 | 只投送聊天气泡区域（`Page.captureScreenshot` 支持 `clip`） |
| 法律 | 不伪造签名、不重放私有 API、不绕过登录 | 本方案只做"本机已登录客户端的显示与输入转发" |
| VS Code 主题 | 镜像不跟随主题 | 面板边框/工具栏跟随；画面区用中性底色 |
| 高 DPI | 坐标错位 | 用 `devicePixelRatio` 换算，M2 内解决 |

---

## 7. 结论

- **要 1:1 → 路线 A（截屏投送 + 输入转发）**，本机实测数据支持：47 fps 原始流、可降到 10 fps、单帧 67 KB。
- 路线 B（移植官方代码）**不可行且越界**；路线 C（DOM 快照）交互不可用。
- 建议保留"文本模式"，新增"镜像模式"，两者一键切换：
  - 需要**读**答案 → 文本模式（可复制、跟随主题）
  - 需要**看/操作**豆包 → 镜像模式（像素级一致）
